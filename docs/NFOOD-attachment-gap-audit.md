# NFOOD — Attachment Gap Audit

## حالة الملف

تم حفظ الملف المرفق كاملًا داخل المشروع في `docs/NFOOD-global-dashboard-branding-requirements.md`، ويحتوي على 1022 سطرًا من متطلبات لوحة التحكم العالمية والتخصيص حسب الباقة.

## متطلبات موجودة في المشروع

توجد بالفعل بنية Dashboard RTL/LTR، شريط جانبي متعدد الأدوار، Topbar، اختيار المطعم والفرع، البحث الشامل، مبدّل اللغة، الثيم الفاتح/الداكن، بطاقات الوصول السريع، كثافة تشغيلية محسنة، مركز تشغيل للطلبات المتأخرة، Feature Access وعزل المستأجرين، وإعدادات هوية أساسية للمطعم مثل الاسم والشعار واللون والوصف والثيم العام.

كما توجد بنية الباقات والميزات وحدود الفروع وبعض مقاييس الاستخدام، ومكوّنات المنيو العامة والسلة والحجز والـQR والشاشات والعروض، إضافة إلى تقارير الأداء وواجهات التسعير والتدقيق.

## متطلبات موجودة جزئيًا وتحتاج ربطًا أو إظهارًا أوضح

تخصيص لوحة المدير لكل مستخدم، قوالب Dashboard حسب الدور، ترتيب Widgets وحفظها، مستويات Comfortable/Compact/Spacious، Action Center الموحد، Smart Insights النصية، ومقارنة الباقات موجودة على شكل أجزاء متفرقة وليست تجربة Settings → Branding / Subscription مكتملة.

تخصيص الهوية حسب الباقة موجود في طبقة الوصول والميزات، لكن يحتاج إلى Matrix ديناميكية واضحة للهوية، حالات ON/OFF/LIMITED/ADD-ON، رسائل Upgrade، Brand Lock، وواجهة Super Admin لمشاهدة هوية مطعم محدد وإعادة ضبطها أو عمل Override.

محرر الألوان والثيمات وقواعد التباين، تخصيص الخطوط، favicon، الشعارات الفاتحة والداكنة، الغلاف، ومعاينة الهوية الحية تحتاج إلى توحيد في Visual Branding Editor بدل توزيعها على إعدادات منفصلة.

## متطلبات تحتاج استعادة أو تنفيذًا مخصصًا

الملف يطلب تجربة Branding Editor كاملة مع معاينة حية، Semantic Tokens مستقلة بين NFOOD والمنيو العامة، تحكمًا فعليًا في White Label وPowered by NFOOD وCustom Domain حسب الباقة، مصفوفة Features/Limits ديناميكية في Super Admin، Usage Meter موحد، Preview Before Upgrade، وتخصيصًا متسقًا للمنيو والسلة والدفع والتتبع والحجز وQR وشاشات العملاء.

كما يطلب الملف جعل الفروق بين Free وStarter وProfessional وEnterprise واضحة وظيفيًا، مع الاحتفاظ بإعدادات الهوية عند خفض الباقة وتعطيل الميزات فقط، ثم إعادة تفعيلها عند الترقية، مع تحقق Backend قبل حفظ أي تخصيص مدفوع.

## قرار الاستعادة

لن يُعاد بناء المشروع من الصفر. ستتم الاستعادة على مراحل فوق المكونات الحالية: حفظ المتطلبات، إنشاء قاموس Features للهوية والتخصيص، ربطه بالباقات والـOverrides، بناء واجهة Branding Editor ومعاينة حية، ثم إضافة تخصيص Dashboard وUsage/Upgrade UX، مع اختبارات عزل وصلاحيات وتحقق بصري.
